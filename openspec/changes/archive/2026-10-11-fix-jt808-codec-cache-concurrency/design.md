## Context

动机见 [proposal.md](proposal.md)，行为契约见 [spec.md](specs/jt808-codec-cache-concurrency/spec.md)。

当前实现具有以下与方案直接相关的特点：

- `Jt808AnnotationBasedDecoder` 作为共享实例，按解析器类缓存自定义字段解析器；同一解析器可能处理不同连接和不同消息字段。
- `ExtendedJt808FieldDeserializerLocationExtraItem` 使用两个普通 `HashMap` 保存 key 映射和默认描述符，循环内先发布内层 map 再填充内容，最后写默认描述符。
- `Jt808AnnotationBasedDecoder`、`Jt808AnnotationBasedEncoder` 的转换器实例缓存都是普通 `HashMap`，采取锁外读、`synchronized (this)` 内二次检查和反射构造。锁外读取不受写入锁保护。
- 位置附加项每次解析创建 `LinkedHashMap` 结果；临时内容由现有 `finally` 释放，基础转换器未匹配时继续嵌套对象解码。
- 字段元数据已有合并注解缓存；长度由现有长度提取器按正数 `length`、非空表达式、长度方法选择，条件与动态长度在当前请求上求值。
- 本地 `v2.3.0-rc.4`、`v2.3.0` 与当前版本的位置附加项解析器相同；共享支持模块的编译目标为 Java 8。

## Goals / Non-Goals

**Goals:**

- 为字段解析配置和转换器实例建立完整、安全的发布边界。
- 在缓存命中路径保留直接读取，实际报文转换不进入配置构建的同步区域。
- 只调整内部缓存及相关测试；使用既有公开 API 和语义验证兼容性。

**Non-Goals:**

- 修改注解定义、别名、默认值，增加 key 范围或重复 key 校验，新增配置选项。
- 修改长度计算、零长度行为、畸形报文校验或现有非竞态异常契约。
- 改变转换器注册机制、反射构造方式、实例生命周期，或使用户自定义转换器内部状态自动线程安全。
- 全面改造元数据、缓存淘汰、热更新、线程池、Netty 流程、Spring 自动配置或其他协议模块。
- 将 issue 报告的长期生产事故认定为本次已复现的故障。

## Decisions

### 1. 同一字段的全部描述符作为一个配置对象发布

在附加项解析器内部新增私有静态配置类，将 `Map<Integer, RequestMsgConvertibleMetadata>` 和默认描述符作为 `final` 成员。在局部变量中完成整个注解数组及默认描述符的构建后，再返回完整对象；内部 map 使用 Java 8 可用的只读包装，且构建后的可变引用不得逃逸。

用 `ConcurrentMap<Field, ...>` 替代两个成员缓存。继续使用实际 `Field` 作为键，避免同名字段或相同附加项 key 在不同消息类之间串用。描述符仅来自既有字段元数据中的合并注解，缓存不保存请求、`Context`、缓冲区或结果。

替代方案：将所有 map 换为并发容器仍会发布未填完的映射；保持两个缓存则仍需解决二者的初始化一致性。单一完整配置对象能明确消除这两个窗口。

### 2. 配置缓存采用命中直接读取、未命中完整计算

先 `get(field)`，未命中时使用 `ConcurrentHashMap.computeIfAbsent()` 仅构建描述符。构建成功前不得向缓存写入配置；抛异常时不得留下部分内容。构建回调不创建用户目标对象、不调用基础转换器、不执行嵌套解码，也不递归访问同一配置缓存。

保留 `getValueType()` 在实际附加项循环中的惰性查询位置，避免将配置初始化前移到无附加项或被条件跳过的路径。缓存命中时直接读取完整配置，发布后不再修改内部映射。

先 `get()` 也避免部分 Java 8 实现中缓存命中仍进入 `computeIfAbsent()` 同步路径。配置构建成本与注解数组大小相关，不将整个报文解析串行化。

替代方案：给所有类型查询加一把实例锁也能保证安全，但会让每个附加项的命中查询经过同一锁；启动预热不能覆盖所有首次使用的自定义字段。

### 3. 转换器实例缓存保留既有同步构造流程

对注解解码器和编码器，优先仅将转换器缓存替换为 `ConcurrentHashMap`，保留已有的 `get()`、`synchronized (this)`、二次检查、`ReflectionUtils.createInstance()` 和构造成功后 `put()` 的流程。这样锁外读取由并发容器保证安全，成功创建仍按类复用，现有反射异常包装和构造同步范围保持不变。

此前讨论中的 `computeIfAbsent()` 构造转换器也是一种实现方式，但本次兼容性约束下不采用它：用户自定义构造逻辑没有必要进入并发容器的计算回调，也不需要改变不同转换器类之间的既有构造同步方式。实际 `deserialize()`、`serialize()` 调用继续在构造锁之外执行。

不将实例缓存变为 `static`、线程局部或按字段保存。解码器和编码器分别保留自身实例生命周期。

### 4. 注解语义逐项沿用，不借机引入校验或新异常

配置构建按注解数组顺序执行 `put()`，保留后声明覆盖先声明。默认描述符直接取 `defaultKeyValueMapping()`，包括显式 `byte[]`、隐式 `ByteArrayContainer` 和其他现有受支持组合。不得因本次修复修改注解文件或内置消息的描述符。

完整对象总是具备默认描述符，因此不再使用“默认缓存尚未写入”的临时 `BYTES/byte[]` 兜底；该兜底属于不完整初始化状态，不是正常注解默认值。空映射仍创建完整配置对象，所有项使用默认描述符；这是落实现有默认项语义，不改变注解定义。

保持合并注解获取路径；不新增“缺少注解”的自定义异常，不调整非竞态错误的捕获和包装，不为重复 key 或不可在一字节 key 中出现的声明增加拒绝逻辑。

实际 `deserialize()` 中的读取、转换、结果 `put()`、释放代码保持原有结构。内部配置只读不意味着返回结果只读；结果仍为每次调用创建的可变 `LinkedHashMap`。长度大于零时切片、长度为零时按当前剩余输入解析的现有行为也保持不变。

### 5. 通过结果、实例和资源契约验收

在 `jt-808-server-support` 的既有测试结构中增加以下验证：

- 使用共享的新解码器、启动屏障和每个线程独立的输入缓冲区验证并发首次解析，断言 key 对应的运行时类型和具体值，而非仅断言无异常。
- 用测试侧注解/描述符替身及同步信号暂停配置构建，触发另一个请求对尚未构建的 key 或默认项进行解析，验证其不会读取半成品。设置超时、传播工作线程异常，在 `finally` 中解除屏障及关闭线程池；不通过生产公开 API 暴露缓存或测试钩子。
- 验证显式/隐式默认描述符、重复注解 key、空映射、跨字段隔离、报文重复 key 的覆盖及迭代顺序、返回映射可修改且相互独立。
- 用现有编解码入口覆盖字段顺序、条件跳过、三种长度来源及优先级、不同消息实例的动态长度、空输入与零长度边界。
- 用可计数的自定义转换器验证每个编解码实例中同一类只成功构造并复用一个实例、不同编解码实例隔离、构造失败异常包装不变；通过具体值和编码字节检验转换路径。
- 验证基础转换器和嵌套对象路径，检查成功与转换失败路径上的临时缓冲区释放，并保留调用方对输入缓冲区的释放责任。
- 对照现有公开签名和注解定义验证无源码/二进制接口变更；复用既有消息样例，无需引入 API 检查库。

受控窗口测试负责发现半成品发布，重复并发测试补充覆盖多字段和缓存命中；不将随机压力测试作为唯一证据。不要求通过损坏 `HashMap` 内部结构来复现问题。

## Risks / Trade-offs

- [初始化回调可能被扩展为报文处理] → 仅允许读取注解和构建描述符；转换及嵌套解码保持在回调之外。
- [只读包装使结果不可修改] → 只包装私有配置，返回结果保持独立且可变，并增加修改结果的回归场景。
- [兼容性修复夹带其他边界行为变化] → 不改注解、长度提取器或反射工具；以具体场景验证重复 key、默认类型、零长度和异常包装。
- [构造锁依然串行化不同转换器的首次创建] → 保持原有构造方式以降低兼容风险；命中查询与实际报文处理不进入构造锁。
- [并发测试误用同一个可变输入或吞掉线程异常] → 为每个请求创建独立输入，通过有时限的任务结果收集断言失败，并保证清理线程池和缓冲区。
- [旧实现的空映射会抛空指针] → 将空映射默认解析作为明确的缺陷修复验收项，不将缓存缺失异常视为注解语义。
- [运行时矩阵受本机工具链限制] → 保持 Java 8 编译/API 目标，验证 Java 8 与报告中的 Java 17 运行环境以及相关 starter 兼容性；记录实际执行矩阵和限制，不将仅编译通过等同于 Java 8 运行验证。
- [修复完成后无法直接证明生产事故因果链] → 发布说明只描述已确认的并发初始化与安全发布修复。

## Migration Plan

无需用户迁移。实现完成后运行本变更的针对性回归和支持模块既有测试，检查公开接口与注解无变化，并记录已验证的平台矩阵。交付仅包含内部缓存修复和必要测试，不增加预热配置或新的操作步骤。

本次规划不自动发布版本或向其他分支回移补丁；若后续回移至 2.x，使用同样的行为契约和对应分支的构建验证。回退代码或版本可以恢复原实现，但会重新引入已确认的竞态。
